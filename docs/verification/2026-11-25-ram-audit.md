# RAM audit checklist run (2026-11-25, Windows)

Source: `Ram_Audit_Checklist.md`. This is a **read-only audit** on a Windows host; Linux-only items are marked N/A rather than guessed. No files were deleted and no services were changed.

## Snapshot

- Physical RAM: 15.71 GB total, ~4.07 GB free at the end of the audit (it ranged from 0.43 GB during an active Playwright suite to 4.43 GB after it finished).
- Commit charge: ~35.2 GB against a 22.3 GB pagefile (current pagefile use ~4.1 GB, peak ~4.6 GB).
- Memory Compression working set: ~94 MB. Nonpaged pool: ~1.1 GB.

## 1. OS and kernel

- **buff/cache vs available**: Windows does not expose Linux `buff/cache`; available physical memory was used instead. The earlier 0.43 GB reading was transient pressure from the active browser suite, not a stuck cache.
- **Unlinked open files**: not checked. Needs `handle.exe` or equivalent; not installed, and no destructive cleanup was authorized.
- **tmpfs / RAM-backed files**: N/A on Windows for `/dev/shm`, `/run`, `/tmp`. `%TEMP%` holds 161,037 files / ~14.8 GB on disk. Disk pressure, not RAM; left untouched.
- **HugePages**: N/A on Windows.
- **Compressed RAM**: Memory Compression ~94 MB, modest. No `zram`/`zswap` equivalent.
- **Zombie/orphan processes**: Windows has no `Z` state. 101 of 104 `node.exe` processes have a non-node parent, which is normal for MCP/CLI children; no evidence of orphaned trees.
- **Kernel modules/eBPF maps**: N/A on Windows for the Linux tooling named in the checklist.

## 2. AI, ML and agent processes

- **Local inference servers**: no `ollama`, `llama-server`, `vllm`, `lmstudio` or `mlx` process running. Ollama CLI is installed but its service was down; the Creative Muse worker is expected to start it.
- **MCP subprocesses**: 72 `node.exe` processes have `mcp` in the command line, ~1.6 GB for all 104 node processes combined. This is the largest agent-specific cluster, but each is a live MCP server; none was stopped.
- **Vector databases**: no `qdrant`, `chromadb`, `milvus`, `weaviate` or `faiss` process.
- **PyTorch / DataLoader workers**: 25 `python` processes, ~159 MB total. No CUDA/MPS host-buffer evidence.
- **mmap model weights**: no process matching safetensors/Hugging Face/ONNX Runtime patterns.
- **Agent state caches**: the long-running OpenCode sessions hold most of the `opencode` RSS (~401 MB and ~238 MB). This is expected for the coordinator and one worker.

## 3. Browsers, headless engines and Electron

- **Headless automation**: a stale `headless_shell` tree (4 processes, ~150 MB) was observed after a completed Playwright run and then exited on its own. No stale tree remains.
- **Chrome**: 29 processes, ~1.96 GB. This is the user's browser with ChatGPT/Gemini tabs; left untouched.
- **Electron**: 18 `msedgewebview2` processes (~942 MB), 11 `Wispr Flow` processes (~283 MB), 8 `copilotapp` processes (~80 MB). All appear to be active desktop integrations; not killed without a use-case decision.
- **Extension hosts / service workers**: not separately inspected; covered by the Chromium process trees above.

## 4. Runtimes, build tools and LSP

- **LSP**: no `tsserver`, `pyright`, `pylance`, `rust-analyzer`, `clangd`, `gopls`, `jdtls` or `ruby-lsp` process found.
- **Node dev servers/watchers**: one `vite` process, 6 Playwright-related node processes, 3 `langgraph` processes. The Playwright processes belonged to a finished suite and have since exited.
- **JVM/Gradle daemons**: none.
- **Python workers**: the 25 python processes are small (~159 MB) and tied to MCP/uv tooling.
- **File watchers**: no `watchman` process found.

## 5. Containers, VMs and orchestration

- `wslservice` 1 process / ~4 MB; no `vmmem`. No `dockerd`, `containerd` or BuildKit process. No container-mode cgroup checks apply on the host.

## 6. Databases and caches

- `postgres`: 10 processes, ~18 MB. No `redis`, `memcached`, `elasticsearch` or ClickHouse process. No cache pressure found.

## 7. Services, telemetry and sync

- `MsMpEng` (Defender): ~397 MB — security software, left alone.
- `SearchIndexer`: ~131 MB, plus 5 `SearchFilterHost` processes. It may be indexing the 14.8 GB temp tree; pausing it would need elevated service control (the earlier `sc.exe config` was denied).
- `OneDrive`: ~27 MB. `dwm`: ~61 MB. Both normal.
- `DiagTrack` and `SysMain` were running; attempts to set them to Manual were denied without an elevated shell. Registry Run keys were backed up to `%TEMP%\opencode\ram-optimization-backup` before any attempt. No startup entry was changed.

## Verdict

No single hidden leak explains the pressure. It was dominated by live work: Chrome (~1.96 GB), MCP node servers (~1.6 GB across 104 processes), two OpenCode sessions (~0.64 GB), Defender (~0.4 GB) and the active Playwright suite when it ran. The biggest safe win was simply letting the finished browser suite exit; RAM recovered from 0.43 GB to about 4 GB. Deleting `%TEMP%` would free disk, not RAM, and was not done. Elevated service changes and browser tab cleanup need the user's explicit call.
